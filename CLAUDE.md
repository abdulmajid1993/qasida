# CLAUDE.md

Guidance for Claude Code (and humans) working in this repository.

## What this project is

**Sacred Lyrics** — a React single-page app for reading the lyrics of
**Qawwali**, **Qasida**, and **Ilahi** devotional poetry, each shown with its
original-language text alongside an English translation.

The deployed app is a Create React App (CRA) project living in `app/`. The
`lyrics/` folder holds the **source-of-truth PDFs** the lyric data was
transcribed from.

## How the app is wired

- `index.js` renders `App` from `App.jsx`.
- `App.jsx` is also the **router**: it keeps a `section` state and shows
  `Homepage`, the Qawwali view, `QasidaBook`, or `IlahiBook` accordingly.
- Each collection file exports a component plus a top-level data array
  (`qawwalis`, `qasidas`, `ilahis`). **The lyrics are hard-coded data in these
  `.jsx` files** — there is no database, API, or external content source.

### The lyric data shape (important)

Every song is an object. Verses (and the chorus) carry two strings:

```js
{
  original:    "Line one\nLine two\nLine three",   // original-language text
  translation: "Line one\nLine two\nLine three",   // English translation
}
```

**Line breaks are encoded as `\n` inside the string.** The UI renders each
verse with `verse.original.split("\n").map(...)` and the same for
`translation` (see `App.jsx` ~line 1787/1805, and the equivalents in the other
collection files). This has a direct consequence:

- A **missing `\n`** fuses two lines into one on screen
  (e.g. `...ends everythingYour praise...`) → looks "displayed wrong".
- An **extra/dropped line** changes how many lines appear → looks "cut out".

So most "lyrics displayed wrong / cut out" bugs are **data bugs in the `\n`
structure of a single string**, not rendering bugs.

Other per-song fields you'll see: `id`, `title`, `language`, `poet`,
`introCount` (how many leading verses are labelled "Intro" instead of
"Verse N"), and optional `chorus`. Qasida entries may also use
`arabicChorus` / `qasidaChorus` flags.

## Source of truth & a critical caveat

The PDFs in `lyrics/` are the reference for **correct line/paragraph breaks**.
When fixing how a verse is split, check the PDF.

**However, the app is NOT a 1:1 transcription of the PDFs.** Several songs in
the app are *fuller or different renditions* than the PDF (extra verses, a
chorus, and English translations the PDF does not contain), and the Qawwali
collection contains more songs than the Qawwali PDF covers (~33 in the app vs.
14 in `Qawwali_v2.0.pdf`). The Ilahi collection has **no** PDF at all.

➡️ **Do not do a blind "line-for-line replace the app with the PDF" pass.** It
will delete real content and translations from sacred text. Fix the specific
broken break (insert/remove the right `\n`), preserving existing content.

## Editing lyrics safely

This is religious text. Be precise and conservative.

- Change only the `\n` structure / wording that is actually wrong; don't
  reflow or "tidy" verses that already render correctly.
- A reliable signal for a fusion bug is a `lowercase` letter immediately
  followed by an `UPPERCASE` letter *within a line* — BUT beware many false
  positives: Roman-Urdu transliteration legitimately capitalizes mid-line
  (`meN`, `haiN`, `BeKasoñ`, `JalwaGari`, `SubhanAllah`). Verify against the
  PDF or known lyrics before "fixing".
- Original and translation line counts do **not** need to match — translators
  often render two original lines as one English sentence. A mismatch alone is
  not a bug.
- Edit `App.jsx` / `QasidaBook.jsx` / `IlahiBook.jsx`. **Never** edit
  `App_original.jsx` (dead snapshot) or files under `build/`.

## Common commands

All commands run from the `app/` directory:

```bash
cd app
npm install        # first-time setup (node_modules is not committed)
npm start          # dev server at http://localhost:3000
npm run build      # production build into app/build/
npm test           # CRA test runner (no tests currently)
```

A successful `npm run build` is the cheapest way to confirm a `.jsx` edit
didn't break syntax.

## Inspecting the PDFs

The PDFs are not text-friendly out of the box and the system `cryptography`
package can be broken. Extraction that works reliably:

```bash
python3 -m pip install --quiet --force-reinstall cffi   # if imports crash
python3 -m pip install --quiet pymupdf
python3 -c "import fitz; print('\n'.join(p.get_text() for p in fitz.open('lyrics/qawali/Qawwali_v2.0.pdf')))"
```

The PDFs interleave an original line followed by its English line, with page
headers like `Page N of M` and a dotted table of contents on page 2 — filter
those out when diffing.

## Deployment

Netlify builds from `app/` (`npm run build`) and publishes `app/build`
(see `app/netlify.toml`).

## Conventions

- Styling is inline-style objects (no CSS files / Tailwind). Match the
  surrounding palette (teal `#2c6e6a`, gold `#c9a84c`, serif fonts).
- Keep new code idiomatic to the existing file it lives in.

## ⚠️ Mobile & tablet first (REQUIRED for any visual change)

**This application is used overwhelmingly on tablets and mobile phones.** Any
frontend / visual change MUST be optimized for small touch screens first and
scale up to desktop second. Treat phone/tablet as the primary target, not an
afterthought.

When changing or adding UI:

- **Use fluid type, not fixed sizes.** Follow the existing
  `fontSize: "clamp(min, vw, max)"` pattern (e.g. `clamp(20px,6vw,34px)`).
- **Use self-collapsing layouts.** Reuse the existing grid pattern
  `repeat(auto-fill, minmax(min(100%, 300px), 1fr))` and `flexWrap: "wrap"`
  so things stack to a single column on narrow screens.
- **No fixed-pixel widths** that can overflow a ~360px-wide phone; prefer
  `maxWidth`, `%`, `flex`, and `min(...)`.
- **Tap targets ≥ ~44px**, with adequate spacing — fingers, not cursors.
- **Don't rely on hover** to reveal anything essential; hover doesn't exist on
  touch. Hover may enhance, never gate.
- The app keeps responsiveness in inline styles (no CSS files, no JS media
  queries) — match that approach. See `docs/responsive-design.md`.
- **Verify on a narrow viewport** (DevTools device toolbar ~375px AND a tablet
  width ~768–1024px) before considering a visual change done.
